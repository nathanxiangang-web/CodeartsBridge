# CodeartsBridge Control Center 开发文档

> 版本：1.0  
> 更新日期：2026-09-19  
> 仓库：nathanxiangang-web/CodeartsBridge  
> 当前阶段：后端控制面基本成型，研发重心转向 UI 设计、UI 功能实现与自举式 Dogfooding  
> 核心目标：**让 4 个 Worker 用 CodeartsBridge 自己开发 CodeartsBridge，并让每一轮 UI 能反过来提升下一轮开发效率。**

---

# 1. 项目定位

CodeartsBridge 不是大型 AI 开发平台，也不是通用 Workflow Engine。

它是：

> **面向多 AI 软件开发的轻量级任务控制平面。**

当前主链路：

~~~text
User
  ↓
Architect AI
  ↓
Task DAG
  ↓
CodeartsBridge
  ↓
Scheduler / Dispatcher / Pipeline
  ↓
W01 / W02 / W03 / W04
  ↓
Patch + Tests + Evidence
  ↓
Review / FIX
  ↓
Integration
  ↓
Main
~~~

当前后端已经具备任务状态机、依赖、租约、优先级、Worker 匹配、工作区隔离、SSH/remote-worktree、超时、恢复、Review、Integration、Telemetry、Cost、Adaptive Scheduling、Pipeline、HTTP API 等能力。

下一阶段的主要问题已经从“Bridge 能不能稳定运行”转变为：

1. 人是否能快速看懂系统当前在做什么。
2. 人是否能从 UI 完成高频控制动作。
3. 多 Worker、多项目、多任务情况下是否仍然清晰。
4. 后端能力是否被 UI 完整释放。
5. Bridge 是否真的能用自己来持续开发自己。

因此本阶段正式进入：

> **Bridge Control Center 1.0**

# 2. 本阶段总原则

## 2.1 Dogfooding 是硬约束，不是演示

从本开发计划开始，除修复 Bridge 本身无法启动的 P0 故障外：

- 禁止绕过 Bridge 直接分配常规开发任务。
- 禁止为了图方便长期手工 SSH 到 Worker 直接执行开发。
- 禁止多个 Worker 共用同一个工作目录修改代码。
- 禁止“代码写完后再补 Bridge 记录”。
- 禁止 UI 功能只做展示、不接真实运行数据。
- 禁止使用假状态、演示按钮、前端硬编码在线状态。

所有正式任务必须尽可能经过：

~~~text
创建任务
→ Bridge Task DAG
→ Worker 自动派发
→ isolated workspace / remote-worktree
→ Thinking / Events 可观察
→ Tests / Evidence
→ Review
→ FIX（如需要）
→ Integration
→ Telemetry 记录
~~~

这条链路本身就是产品验收的一部分。

## 2.2 AI 决定 WHAT，Bridge 决定 WHEN/WHERE/PROCESS，Worker 决定 HOW

- User：决定需求、优先级和重大方向。
- Architect：拆任务、定义验收、处理跨模块设计冲突。
- Bridge：调度、隔离、并发、依赖、超时、重试、Review 流程。
- Worker：只负责自己的任务和文件边界。

## 2.3 先模块化 UI，再并行堆功能

当前前端主体集中在：

~~~text
src/bridge/web/index.html
~~~

约 38KB，HTML/CSS/i18n/路由/API/页面逻辑/Thinking 轮询混在同一个文件。

在此结构上直接让 4 个 Worker 同时开发 UI，会制造严重冲突。

因此必须先完成 UI-00 前端拆分，再进入真正的 4 路并行。

## 2.4 保持轻量运行时

Bridge 当前的重要优势是：

- Python 3.10+
- 生产运行时不依赖 Node
- 静态 Web UI
- 部署简单

Control Center 1.0 第一阶段不引入 Next.js/React/Vite 作为生产运行依赖。

优先使用浏览器原生：

- ES Modules
- HTML
- CSS
- Fetch / EventSource
- 可复用 JS Components

允许 Playwright 作为开发/CI 测试依赖，但不进入生产运行时。

# 6. Wave 0：建立可并行前端基础

## UI-00 — 前端模块化拆分
**Owner：W01**

### 目标

把单体 index.html 拆成多文件前端，同时保持当前功能和部署方式不回退。

### 必须完成

- index.html 只保留 App Shell 和资源入口。
- CSS 拆分。
- API client 独立。
- hash router 独立。
- i18n 独立。
- 公共 badge/modal/table/toast 组件化。
- 每个页面独立模块。
- Python server 能正确返回 JS/CSS 静态文件。
- Cache-Control 语义保持正确。
- 当前 Dashboard/Projects/Tasks/Workers/Review/Metrics/Thinking/Settings 全部可用。
- 不引入 Node 生产运行依赖。

### 验收

- 当前 UI 功能无回退。
- pytest 全绿。
- UI 配置语义回归测试更新，不再依赖单文件结构。
- 至少完成一次通过 Bridge 自己派发、执行、Review、Integration 的真实提交。

### Dogfood 要求

UI-00 必须由 Bridge 任务创建，不允许手工在主工作区完成整项改造。

完成后，从 UI-01 开始，其他 Worker 使用新模块化前端基础继续开发。

# 7. Wave 1：四路并行建立 Control Center 主体

## UI-01 — App Shell + Dashboard 2.0
**Owner：W01**

### 页面目标

Dashboard 不再只是统计数字，而是“现在需不需要我处理事情”的控制台。

### 功能

1. Bridge health
2. Daemon status
3. Pipeline status
4. 当前运行任务
5. 等待任务
6. 阻塞/失败任务
7. REVIEW_REQUIRED
8. Worker 使用情况
9. 当前项目进度摘要
10. 人工介入队列
11. 最近失败原因
12. 最近 Integration 状态

### 必须回答的问题

打开 Dashboard 后 10 秒内应能看懂：

- Bridge 是否健康？
- Pipeline 是否在跑？
- 4 个 Worker 谁忙谁闲？
- 当前正在执行什么？
- 谁卡住了？
- 有没有任务需要 Review？
- 有没有任务需要人工处理？
- 当前一轮大概推进到哪里？

### 禁止

- enabled == online
- 把无 heartbeat 的 Worker 显示为在线
- 使用假百分比
- 假进度条
- Demo 数据

## UI-03 — Realtime Event Core
**Owner：W03**

### 目标

减少 Thinking 页和 Task 页对 2 秒轮询的依赖，建立统一浏览器实时事件层。

### 功能

使用已有：

~~~text
GET /api/events
~~~

建立 EventSource。

事件进入统一 store：

~~~text
SSE
 ↓
events.js
 ↓
normalize
 ↓
state/event store
 ├── Dashboard
 ├── Tasks
 ├── Worker Center
 └── Thinking
~~~

### 必须支持

- 自动重连
- last-event/cursor 语义
- 重复事件去重
- 页面切换后不重复创建连接
- SSE 异常时允许降级 polling
- UI 明确显示 realtime / degraded 状态
- 不允许因 SSE 中断导致状态永久停住

# 9. Wave 3：项目体验和全链路自举

## UI-08 — Project UX
**Owner：W01**


~~~text

 └── W04 execution profile
~~~

### 页面目标

用户首先看到逻辑项目，再展开看执行 profile。

# 10. Dogfood Acceptance：四个人必须吃自己的狗粮

**Owner：ALL，W04 负责验收**

Control Center 1.0 不是“页面做完”就完成。

必须进行一轮真实自举开发。

## 场景

由 Bridge 自己管理一个新的 Bridge 改进任务：

~~~text
Requirement:
为 Worker Detail 增加 recent failures 视图
~~~

要求：

1. 从 Control Center 创建或确认任务。
2. Architect 拆出任务/验收标准。
3. DAG 页面能看到依赖。
4. Scheduler 自动选择 Worker。
5. Worker Center 显示 Worker busy。
6. Task Detail 实时显示状态。
7. Thinking 能显示事件。
8. 任务结束进入 Review Center。
9. Review Center 查看 RESULT/TESTS/Evidence。
10. PASS 或 FIX。
11. FIX 时生成后续任务并重新派发。
12. PASS 后 Integration。
13. Dashboard 反映最终状态。
14. Metrics 能记录该轮任务。
15. 整个过程不得手工修改 state.json 来伪造流程。

以上 15 项全部通过，才算“吃自己的狗粮”。

所有页面必须处理：

- empty

- stale

# 15. API 优先原则

UI 不直接读取 Bridge 内部文件系统。

统一通过 API/ViewModel。

如果 UI 缺数据：

> 先补 API contract，再做 UI。

不允许在浏览器中猜内部路径、拼任务目录或复制后端调度逻辑。

---

# 16. 安全收口

Control Center 开始具备真实控制能力后，需要补轻量安全层。

最低要求：

- 支持 API token 或反向代理认证。
- 危险操作二次确认。
- Cancel / Retry / Review / Integration 有统一错误返回。
- 不在 UI 暴露 AK/SK、密码、私有 reasoning。
- 日志保持现有敏感信息清洗原则。

本阶段不建设复杂 RBAC。

---

# 17. 完成定义 Definition of Done

单个任务只有同时满足以下条件才算 DONE：

1. 代码完成。
2. 单元测试完成。
3. 必要的 UI E2E 完成。
4. 无明显跨 Owner 文件污染。
5. Bridge 真实派发执行。
6. Outbox/RESULT/TESTS/Evidence 齐全。
7. 独立 Worker Review。
8. PASS。
9. Integration 成功。
10. main 上回归测试通过。
11. UI 不展示假数据。
12. 文档/API contract 有变化时同步更新。

---

# 18. Control Center 1.0 总验收

完成后，用户应该能够只通过浏览器回答：

- Bridge 健康吗？
- Pipeline 在工作吗？
- 4 个 Worker 谁忙谁闲？
- 当前有哪些任务？
- 每个任务为什么在这个状态？
- 谁阻塞了谁？
- 一个项目整体推进到哪里？
- AI 此刻在干什么？
- 哪些任务需要我介入？
- 哪些任务需要 Review？
- 测试结果是什么？
- 哪些代码已经完成？
- Integration 是否成功？
- 哪个 Worker 最近表现异常？
- 系统本轮开发效率如何？

如果仍然需要经常 SSH、翻 state.json、手工 grep 日志才能回答这些问题，则 Control Center 1.0 不能算完成。

---

# 19. 本阶段暂缓项

为了避免再次把 Bridge 做成大型平台，以下能力暂缓：

- Workflow DSL
- 拖拽式流程设计器
- 大型 RBAC
- 多租户
- 复杂插件市场
- 自建完整 IDE
- 浏览器代码编辑器
- 大型数据库迁移
- 为“看起来高级”而引入重型前端框架

先把已有控制面做得真正可用。

---

# 20. 执行顺序

Architect 应按以下顺序创建任务：

~~~text
1. UI-00 → W01
2. UI-00 PASS + Integration
3. 并行：
   UI-01 → W01
   UI-02 → W02
   UI-03 → W03
   UI-04 → W04
4. Review / Integration
5. 并行：
   UI-05 → W02
   UI-06 → W03
   UI-07 → W04
   UI-08 → W01
6. UI-09 Dogfood Acceptance → ALL
7. Control Center 1.0 Release Gate → W04
~~~

每轮都必须通过 Bridge 的真实调度和工作区隔离执行。

---

# 21. 最终原则

本阶段最重要的不是“把页面画漂亮”。

而是：

> **把 CodeartsBridge 从一个后端能力很强、需要懂内部结构才能操作的工程工具，变成一个可以真正指挥 4 个 AI 工程师持续开发的软件工程控制中心。**

并且这个控制中心必须证明自己有用：

> **它必须先让开发它自己的 4 个 Worker 工作得更快、更清楚、更少冲突。**

这就是本阶段的 Dogfooding 标准。
