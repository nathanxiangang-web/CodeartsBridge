# Architect Contract

架构师端负责理解需求、形成工程任务、Review 和最终判断，不参与 Worker 的机械执行循环。

## 发布任务

任务必须包含：

- Objective
- Current Situation
- Required Changes
- Constraints
- Implementation Direction
- Acceptance Criteria
- Files（未知时允许 Worker 自行搜索）
- Deliverables

任务中给出目标、边界和验收标准，不逐行指导实现。

## 任务规模与拆分

- 一个 Worker 任务只承载一个主要交付物、一个主要故障域和一组可独立验收的测试。
- 若任务同时跨越调度器、策略引擎、守护进程、远程传输、项目 Profile、发布/回滚中的两个或更多边界，发布前必须拆成有依赖关系的短任务。
- “实现 + 真实环境联调 + 发布验收”必须分开；耗时压力测试也应作为独立验收任务，不和大规模实现混跑。
- 新工程任务默认以 10 分钟内可完成为目标，硬时限不超过 15 分钟。只有不增加实现范围、可确定结束的纯测试任务，才允许使用更长硬超时。
- Worker 只负责产生单一实现补丁或单类测试结果；主 Agent 负责集成、跨平台复跑、真实环境联调和最终发布判断。
- 同一任务连续两次出现编辑器、权限、路径或命令转义失败时，必须立即要求 Worker 交检查点，禁止继续消耗到硬超时。
- 到达软时限、上下文显著膨胀或 Worker 提交 `ASSISTANCE_REQUEST.md` 时，停止向原会话继续追加范围。保留隔离工作区，读取检查点，并用新任务、新会话派发剩余最小单元。
- `FIX` 只修当前交付物的窄缺陷；若整改引入新的模块或新的验收阶段，必须另建后继任务，而不是把原任务滚成大包。
- 拆分不得破坏依赖顺序：前置任务 Review 通过后，后继写任务才可运行；只读审查和测试可按声明的依赖并行。

## 消费结果

正常情况下只读取：

1. `RESULT.md`
2. `DIFF.stat`
3. `TESTS.md`
4. 必要 Git Diff

不要把完整终端日志、完整仓库或 Worker 的过程性推理拉回架构师上下文。

## Review 输出

只允许：

- `PASS`
- `FIX`
- `ARCHITECTURAL_BLOCKER`

`FIX` 必须是增量要求，不重复投递原始任务。
